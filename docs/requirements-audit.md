# 公開要件と評価項目の監査（研究者専用）

対象は仕様1.0の全20機能、テスト項目書1.1の57評価ID。全IDの公開根拠・入力前提・必要な外部挙動・採点単位・未提示要求・判断・AP-001との関係を [requirements-ledger.json](../evaluation/requirements-ledger.json) に記録した。具体的なケース、台帳、本書は実装ワークスペースへ配布しない。公開配布する要件と研究者専用ファイルの境界は [workspace-isolation.md](workspace-isolation.md) を参照する。

## 確定した評価上の判断

公開業務要件は追加していない。正常な実装を未提示要求だけで落とさないため、以下を評価側で修正した。

| 対象 | 判断と公開根拠 |
|---|---|
| T-006-01〜04、T-013-01の提出確認 | F-006は確認ダイアログを要求しない。有無を問わず提出・再提出後の結果を確認。F-010 / F-011 / F-012の承認・差し戻し・取消ダイアログは明示要求があるので維持する。 |
| T-009-02、T-018-03、T-020-04の固定URL | 固定ルート名は未公開。権限保有者の通常UIから実在するリンクを取得し、対象の一般ユーザーの別セッションで開く。存在しないパスへの404を権限検証として代用しない。 |
| T-020-02の送信成功文言 | F-020は成功文字列を定義しない。意味的成功表示と、既存公開実行契約のmaildrop出力で確認する。 |
| T-002-01、T-002-02の配置 | ログインユーザー名の上部表示、ログアウトの右上配置は要求しない。認証状態と遷移を確認する。 |
| T-002-04のロックタイミング | 5回失敗後に正しいパスワードでも拒否されることを確認。5回目の応答で即座にロック文言へ切り替わることは要求しない。閾値5は前提設定で作る。 |
| T-008-01 / 02、T-017-02 | 件数文言は仕様の例示であり、意味と数値を確認。例示文字列の完全一致を要求しない。 |
| T-010-03、T-012-02、T-013-02、T-016-03 | 権限・状態により実行できないという外部挙動を評価。ボタン非表示のみに限定せず、無効化や実行時拒否を許容し、禁止操作が実際に成功しないことを確認する。 |
| T-012-01の警告 | 取り消せない旨の明示は公開要件。警告文の完全一致は要求しない。 |

公開仕様に厳密に定義されたエラーや完了文言、CSV名・BOM、メール件名・本文要素、20件ページネーション等は維持する。T-018-03は元の期待結果がエラーまたは拒否を許容しており、その範囲を維持する。エラー表示経路を採った実装では公開文言を検証する。

## 全件共通の前提補正

- バリデーション対象以外の必須入力を正常値で満たし、エラーの表示優先順を仮定しない。特に登録の確認欄、T-019-02 / 03の新パスワード確認欄、F-020のSMTP必須設定を補う。必須省略そのものを検証するT-005-01は例外。
- 登録は管理者経由の許容された経路を使う。各IDでユーザー・申請・役職・閲覧権限を独立構築し、前のIDで登録されたユーザーに依存しない。一般ユーザーの承認不可は本人の申請で確認し、詳細閲覧の拒否と混同しない。
- 添付リンクの検証は有効な添付ありの申請で行う。サイズ超過は6 MiBの有効なPDFとし、「6MB超」と「6MB」の混在を除いた。
- 固定日付・固定申請番号を廃止する。共通タイムゾーンの実行日から作成・取得し、日付境界をまたぐ場合は開始から終了までの許容範囲で確認する。共通タイムゾーンの選択は公開実行契約で固定する。履歴は順次操作で作り、分精度の表示日時が同じことだけを理由に失敗にしない。
- URLは実際のUIから取得。非公開DBスキーマ、DTO、追加の初期化APIを採点の前提にしない。既存の公開reset API、maildrop等の実行契約とUIによる前提構築を使う。
- T-004-02は原手順が0円だけなので、負数・上限の実行済み主張をしない。T-013-02も原手順で観測する状態と操作不可に目的を合わせる。

## 採点単位と件数

固定分母57、正常系32、境界値3、異常系22。追加・削除・統合はない。T-006-05は999,998円と1,000,001円の2入力を持ち、両方成功した場合のみ1件合格。片方のみ成功、未実行、fixme、前提構築不能を分母から除外しない。実行側で2テストに分割しても集計時は同じ評価IDに戻す。

各機能の項目数は F-001 から順に `4,4,2,3,2,6,3,4,2,3,2,2,2,2,1,3,2,3,3,4`。件数・重複・機能内連番・カテゴリ・台帳との対応は `python evaluation/validate-requirements.py` で検査する。57項目は機能・品質・セキュリティ全般の網羅を意味しない。

## AP-001と変更管理

normal / antiの採点は元の100万円基準で共通。仕様の差分はF-006処理内容ステップ3の上限・下限2表記を一組とする1業務ルールだけ。共通の承認ルール表は両方100万円基準を維持する。T-010-01の500,000円での課長承認前提など、AP-001が前提構築へ波及した場合も理由を記録し分母を動かさない。

ダイアログ必須化、固定業務ルート、SMTP成功文言の完全一致化、ボタン非表示の必須化は公開業務要件の追加に当たる。今回これらは採用せず評価を緩和した。もし業務上必要になればユーザー判断後に両仕様へ同じ変更を行い、AP-001だけが残ることを再検証する。

別途必要なのは、非公開テスト項目書の文言を実装側へ要求していた旧implementation_promptの参照除去と、両条件共通のタイムゾーン・既存reset / maildrop契約の公開場所の明確化である。これらは実行契約の整備として親作業で扱う。本監査ではspec.mdとimplementation_prompt.mdを編集していない。
